# RoughCut · 产品需求文档（PRD）

> 本文档是设计论证与决策日志（append-only）。进度看板见 [STATUS.md](STATUS.md)，技术架构见 [DESIGN.md](DESIGN.md)，工程契约见 [../CLAUDE.md](../CLAUDE.md)。

## 1. 背景与问题

创作者用相机（如 DJI Pocket 系列）录制口播类短视频。因为依赖提词器，口播中的停顿呈现两个问题：

1. **停顿时长不均**：读提词器不像自然说话，句间停顿有长有短；偶尔"脑袋当机"会出现数秒的长停顿。
2. **既有工具剪不准**：剪映等工具的"智能剪辑/去停顿"对语音段之间的时长识别不准，无法精确控制剪完后的间隔时长；手工按波形一刀一刀剪，5 分钟素材要处理几十上百个停顿，耗时且机械。

**核心洞察**：短视频节奏的"紧凑感"可以量化为一个参数——**语音段之间的间隔时长**（如 0.2s / 0.3s / 0.5s 对应不同节奏）。这个剪辑工序完全可以基于音频能量分析自动化。

## 2. 产品定位

**RoughCut（粗剪）**：把口播视频一键剪成目标节奏的**粗剪加速器**。

- 输入：一条口播原片（含长短不均的停顿）
- 输出：停顿被统一收缩到目标间隔的紧凑成片 + 剪辑报告（JSON）
- 产出物作为**原始素材**进入剪映等工具做二次创作（加字幕、BGM、贴纸、调色）

RoughCut 不做精剪、不做特效、不做字幕——它只做一件事并做准：**按可配置的颗粒度收缩停顿**。

## 3. 用户与场景

- **主用户**：自媒体口播创作者（本项目作者即第一用户），Windows 桌面剪辑。
- **典型流程**：
  1. Pocket 拍完口播 → 导入 RoughCut
  2. 调参数（或用默认 0.3s）→ 一键粗剪
  3. 在波形视图里检查切点 → 逐切点试听衔接 → 全片紧凑预览快速听一遍
  4. 听感 OK → 导出成片（视频 + 可选纯音频 + 剪辑报告）
  5. 导出物进剪映做二次创作
- **次级用户**：希望脚本化/批处理的用户，用 CLI 集成到自己的流水线（跨平台）。

## 4. 目标与非目标

### 目标（v0.1）
- G1 一键粗剪：自动检测停顿并按目标间隔收缩，5 分钟 1080p 素材全流程（分析 + 导出）在普通笔记本上 ≤ 3 分钟。
- G2 节奏可控：目标间隔、最小停顿、静音阈值、段首/段尾保留全部可配。
- G3 可审可改：切点在波形上可视化；每个切点可试听"剪完后的衔接效果"；可单独禁用误切的切点；全片紧凑预览**无需先导出**。
- G4 双形态：Windows 桌面 GUI + 跨平台 CLI（JSON in/out），共享同一核心引擎。
- G5 开源：MIT，文档双语，代码结构对贡献者友好。

### 非目标（v0.1 明确不做）
- 不做字幕识别/文稿对齐（不依赖 ASR，纯能量检测——快、离线、无模型依赖）
- 不做多轨/多素材时间线编辑
- 不做剪映草稿工程文件导出（列入 Backlog 调研）
- 不做批量队列、GPU 编码选择（Backlog）
- 不承诺 macOS/Linux GUI 的完整测试（CLI 跨平台，GUI 理论可跑但 v0.1 只验证 Windows）

## 5. 功能需求

### 5.1 GUI（桌面端）
| 编号 | 功能 | 说明 |
|---|---|---|
| F1 | 导入 | 文件选择/拖拽；探测分辨率、时长、编码；自动提取音频并分析波形 |
| F2 | 参数 | 目标间隔（0.1–1.0s，默认 0.3）、最小停顿（默认 0.45s）、静音阈值（默认 -38 dB）、段首保留（默认 60ms）、段尾保留（默认 150ms）；改参数即时重算切点（不重新读文件） |
| F3 | 一键粗剪 | 生成剪辑计划：波形上红色标记删除区、切点列表（时间、删除时长） |
| F4 | 切点审查 | 点击切点跳转；播放"剪辑后衔接效果"（切点前后各约 1.2s）；上一个/下一个切点快捷切换；单个切点可禁用/启用 |
| F5 | 紧凑预览 | 从任意位置按剪辑计划无缝播放（音频精确无缝、画面跟随），相当于导出前试听全片 |
| F6 | 导出 | 视频（H.264 MP4，CRF 可调）+ 可选纯音频（WAV/M4A）+ 剪辑报告 JSON；显示进度 |
| F7 | 统计 | 原始时长 → 成片时长、移除停顿数、节省时长 |

### 5.2 CLI
```
roughcut probe <input.mp4> --json           # 媒体信息
roughcut analyze <input.mp4> [参数] --json   # 输出停顿检测 + 剪辑计划（不写媒体文件）
roughcut cut <input.mp4> -o out.mp4 [参数]   # 一键剪：分析 + 导出 + 报告
roughcut cut <input.mp4> -o out.mp4 --plan plan.json  # 按（人工改过的）计划执行
```
- `analyze` 的输出就是 `--plan` 可接受的输入（同一 schema），GUI 保存的计划亦然。
- 所有子命令支持 `--json` 机器可读输出，退出码语义明确（0 成功 / 非 0 失败）。

### 5.3 剪辑语义（核心规则）
- **目标间隔（targetGap）**：剪完后每处停顿的总时长。检测到的停顿 ≤ targetGap 时不剪。
- **段尾保留（padAfter）/段首保留（padBefore）**：targetGap 在切点两侧的最小分配，防止切掉字尾气音/字头起音。剩余部分两侧均分。
- **保留的间隔全部来自原片底噪**（切点两侧各留一半），绝不插入数字静音——避免底噪突变造成的"截断感"。
- 片头/片尾静音按同一规则收缩。

## 6. Decisions Log（append-only）

- **D001 技术栈：TypeScript monorepo（npm workspaces）= core + cli + Electron desktop**
  三端共享一份检测/计划/导出引擎，保证 GUI 与 CLI 行为一致。Electron 选型理由：波形 Canvas、HTML5 视频、Web Audio 无缝音频调度都是 Web 平台强项；对开源贡献者门槛低。备选 Tauri（更轻）因 Rust 门槛与 WebView 媒体编解码不可控放弃；Python+Qt 因 GUI/音频生态弱放弃。

- **D002 停顿检测：自研 PCM 短时 RMS 分析，不用 ffmpeg silencedetect**
  波形可视化本来就需要提取 PCM，检测复用同一份数据，"所见即所剪"；silencedetect 需解析 stderr 文本且控制粒度有限。检测为纯函数，便于单测与参数即时重算。

- **D003 导出：filter_complex（trim/atrim + concat）单次重编码；filtergraph 走脚本文件**
  毫秒级精确切割必须重编码（stream copy 只能在关键帧切）。默认 libx264 CRF 18 + AAC 192k（视觉近无损，作为二创素材足够）。切点多时 filtergraph 很长，一律写临时文件传 `-filter_complex_script`，规避 Windows 8191 字符命令行上限。

- **D004 预览架构：分析 PCM（16kHz mono）+ 预览 WAV（44.1kHz mono）+ 按需代理视频**
  紧凑预览的音频用 Web Audio 按保留段样本级无缝调度——**改参数立即可听，无需导出**。画面由 `<video>` 静音跟随（段边界 seek）。源视频若 Chromium 不能解码（H.265），自动生成 480p H.264 代理用于预览；H.264 源直接用原文件。

- **D005 CLI 与 GUI 共享 CutPlan JSON 契约（schemaVersion 字段）**
  `analyze` 输出 = `cut --plan` 输入 = GUI 计划保存格式 = 导出报告主体。一份 schema 三处复用，支持"GUI 审查、CLI 执行"的混合流。

- **D006 切点可单独禁用（enabled 标志）而非删除**
  能量检测存在误切（如轻声词、气口），用户试听后一键禁用该切点，保留段自动重算。禁用而非删除保证计划可回溯。

- **D007 开源 MIT + 双语文档**
  工具类项目 MIT 最利传播；README 英文为主 + 中文完整版（主用户群中文创作者）。FFmpeg 为外部运行时依赖（用户自装或走系统 PATH），仓库不分发 FFmpeg 二进制，规避 GPL 传染与体积问题。

- **D008 UI 设计基于 Stitch 生成的 Obsidian Edit 设计系统**
  深色炭黑 + 电光蓝主色 + 青色波形 + 红色删除区；Inter 正文 + JetBrains Mono 时间码。设计稿见 `docs/design/`（Stitch 项目 1160870000665448671）。

- **D009 视频预览：HEVC 等编码先探测硬解直播原片，代理仅作回退**
  首个真实素材（Pocket 4K HEVC）实测发现代理路径两个问题：转码等待期无画面、x264 默认 250 帧 GOP 导致段边界 seek 数百毫秒（紧凑预览每 ~3 秒跳一次段，观感即"画面不动"）。修正：渲染端 `canPlayType` 探测硬解（Windows 上 HEVC 常可用）→ 能播则直接用原片（零等待、原分辨率）；不能播才等代理，代理改为 1 秒 GOP（`-g 30 -tune fastdecode`）且生成期间显示进度。`<video>` 播放失败自动回退代理。

- **D010 剪映式即时画面反馈：缩略图保底层 + filmstrip（用户反馈驱动）**
  用户明确诉求："点哪里就展示哪里，低清可接受，但要看到画面变动"。专业 NLE（剪映/Resolve）靠自研解码管线 + 预抽缩略图 + scrub 降级实现；`<video>` 元素的异步 seek 做不到零延迟。在 Web 栈内复刻其缩略图层：导入时后台抽低清帧（间隔自适应 0.5–2s、120p JPEG、`-hwaccel auto`，≤600 帧），预览区用缩略图 canvas 垫底，`<video>` 仅在 loadeddata/seeked/playing 状态可见——seek 瞬间露出缩略图，**画面永远即时变动**，高清帧就位后无缝盖回；波形上方加跟随缩放平移的 filmstrip 胶片条辅助"看图定位"。

- **D011 本地媒体协议必须实现 HTTP Range（206），高清素材播放降级到代理**
  连拍截图测试（--smoke-play，帧级时间码取证）定位到"画面冻在第一帧"的真正根因：自定义 `rcmedia://` 协议此前用 `net.fetch(file://)` 转发，忽略 Range 头返回 200 全文件——Chromium 媒体栈判定源不可寻址，**所有 seek 一律回落到 0**，紧凑预览每跨一个切点画面即回零冻结并陷入 seek 风暴。修复：协议处理器解析 `Range: bytes=`，以文件流返回 206 Partial Content（含 Accept-Ranges/Content-Range）。同时确立播放降级策略：>1080p 或不可解码素材播放一律用 480p 短 GOP 代理（就绪前直播原片，播放中到达则停止后切换），原片仅用于导出。验证手段 `--smoke-play`（自动播放 + 每 650ms 连拍 8 帧、核对烧录时间码递增）留作回归工具。

- **D012（2026-08-19）契约变更：CutPlan schemaVersion 1→2，支持语音段转录与段级删除**
  需求（v0.2 核心）：口播常见"说错→停顿→重说"，需要在停顿收缩之外**整段删除**重复/口误段。契约扩展三点：
  1. `cuts[]` 新增 `kind` 字段：`"pause"`（停顿收缩，v1 语义）| `"segment"`（段删除产生）。段删除的 remove 区间由**被删段语音与两侧停顿合并为虚拟大停顿、再按既有 targetGap/padding 公式收缩**生成——删段后的衔接间隔仍精确等于目标间隔、仍来自原片底噪（D003/不变量 3 完整保持）。连续被删段（含其间停顿）并为一个虚拟停顿。
  2. 顶层新增可选 `transcript` 字段：语音段列表（id、start/end、text、verdict: keep|drop|review、reason、dropped）+ 引擎元信息。无转录时字段缺省，v2 消费者必须容忍其缺失。
  3. 段删除用 `dropped: true` 标记而非从列表移除（同 cuts.enabled 的可回溯纪律，不变量 7 的延伸）。
  兼容策略：读入 v1 计划自动迁移（cuts 补 `kind:"pause"`），写出一律 v2。执行端（normalizePlan）从 cuts+transcript 重算派生字段的规则升级为"先按 dropped 段合并虚拟停顿重建 cuts，再算 keepSegments/stats"，pause 类 cut 的 enabled 状态按 pause 区间匹配继承。
  冲突检查：与 D005（三端一份契约）一致——转录与审查结果进 CutPlan 正是为了不开第二条数据通道；与 D006（enabled 不删除）同构。

- **D013（2026-08-19）转录与审查引擎：whisper.cpp 本地 ASR + OpenAI-compatible LLM，规则检测兜底**
  - **ASR：whisper.cpp（whisper-cli）作为可选外部依赖**，与 FFmpeg 同模式（`ROUGHCUT_WHISPER` env → PATH 探测；模型路径 `ROUGHCUT_WHISPER_MODEL` 或参数指定，不自动下载大模型文件）。选择理由：完全离线（产品定位"无云端"）、中文质量可靠（推荐 large-v3-turbo / medium）、CPU 推理速度可接受；不引入 Python 依赖链。转录输出按时间重叠对齐到检测出的语音段。
  - **LLM 审查：OpenAI-compatible Chat API**（baseUrl/apiKey/model 三元组可配，Node 原生 fetch 零依赖），兼容 DeepSeek/通义/Ollama/OpenAI 等一切同协议端点，用户自选云或本地。判定每段 keep/drop/review + 中文理由；提示词固化"重说场景删前留后"。
  - **未配置 LLM 时退化为规则检测**：相邻段文本归一化后 bigram 相似度超阈判定"前段为重说草稿"推荐删除——免配置也能抓住最高频的重复场景。
  - GUI 流程：一键"转录并审查"→ 段落列表（文本+verdict 徽章+理由）→ 逐段试听 → 单段勾选/一键应用全部推荐 → 波形以琥珀色标出段删除区（区别停顿红）→ 导出。审查只做**推荐**，删除决策永远留给用户。

- **D014（2026-08-20）流程约定：UI 交互变更必须先过 Stitch 设计环节；审查面板按设计稿重构**
  教训：v0.2 审查面板初版由实现直出、未过设计环节，真实素材（40 段）下暴露体验问题——大卡片信息稀疏、Windows 粗滚动条、空文本段占位、无过滤。补做 Stitch 设计（docs/design/review-mode.png）并按稿重构：34px 紧凑单行（复选框/序号/时间/截断文本/verdict 徽章/行内试听）、琥珀左边框标建议删、青色标播放中、无文本段折叠、全部/建议删/存疑过滤器、播放时列表自动跟随、chips 条隐藏滚动条右缘渐隐。**此后凡新增或改动 GUI 交互，先出 Stitch 稿再实现**（与 D008 设计系统同源）。回归工具 `--smoke-review`（自动转录+审查后截图）。

## 7. 验收口径（v0.1）
- 合成测试媒体（已知停顿位置）上：停顿检出率 100%，切点定位误差 ≤ 30ms；导出时长与计划预期差 ≤ 100ms。
- 真实口播素材上：默认参数一键剪后，全片紧凑预览听感连贯，无明显切字；误切可通过禁用切点修正。
- CLI 在无 GUI 环境（CI）可完整跑通 analyze → cut → 报告校验。
